# Build-time decisions

Some inputs and hardcoded values are hard or impossible to change after the
first apply. If you change one of them on an existing deployment, Terraform
either plans to replace the resource (downtime and possible data loss), or
Google Cloud has no supported way to make the change. This page lists those
inputs so you can decide them before the first apply. Rows about a resource
apply only when the module creates that resource (for example
`create_network = true` or `create_redis_instance = true`).

Other inputs are often assumed to be fixed but are updated in place. Those
changes can still disrupt running workloads. They are listed in a second
table so you know what to expect.

The provider behavior on this page was checked against the `hashicorp/google`
provider source at `v6.50.0`. The module's constraint (`~> 6.0`) allows other
6.x releases, which can behave differently. Always read `terraform plan` before you apply a change to a live
deployment. A replacement shows as `must be replaced`.

Several stateful resources have protections that turn a planned replacement
into a failed apply instead of data loss: `gke_deletion_protection` and
`postgres_deletion_protection` (both default `true`), and
`gcs_force_destroy = false` (the default) for a non-empty bucket. These fail
during apply, so other resources in the same apply may already have changed.
Module-created KMS keys use `prevent_destroy`, which makes Terraform reject
the plan before anything changes. Do not turn these protections off to get
past a failure until you have a tested backup and a migration plan.

## Changes that force replacement or have no in-place path

| Module input (or hardcoded value) | Provider behavior | What happens on an existing deployment | Guidance |
| --- | --- | --- | --- |
| `gcp_region` as the GKE cluster's `location` | `google_container_cluster.location` is `ForceNew`[^gke-location] | Terraform plans to replace the cluster and its node pool. With `gke_deletion_protection = true` (the default), the apply fails instead. | Pick the region before the first apply. To move regions, build a new deployment and migrate to it. |
| `gke_control_plane_cidr` (used only when `gke_enable_private_nodes = true`) | `private_cluster_config.master_ipv4_cidr_block` is `ForceNew`[^gke-master-cidr] | Terraform plans to replace the cluster. | Choose a free `/28` range before the first apply. |
| `gke_enable_private_nodes` | `private_cluster_config.enable_private_nodes` is `ForceNew`[^gke-private-nodes] | Terraform plans to replace the cluster. GKE itself can switch node pools between public and private nodes[^gke-network-isolation], but not through this input. | Decide the private-nodes setting before the first apply. |
| Hardcoded `datapath_provider = "ADVANCED_DATAPATH"` (Dataplane V2) | `datapath_provider` is `ForceNew`[^gke-datapath] | A cluster created on `LEGACY_DATAPATH` is replaced when it is brought under this module. | Read [GKE Dataplane V2 requires cluster replacement](./upgrading-n8n.md#gke-dataplane-v2-requires-cluster-replacement) before applying to existing state. |
| `subnet_cidr` | `ip_cidr_range` uses `ForceNewIfChange` with `IsShrinkageIpCidr`[^subnet-ipcidr]: a new range that contains the whole old range is expanded in place; any other new range forces replacement | Expanding to a larger range that contains the old one is done in place. Shrinking the range, or moving it to a different range of any size, plans replacement of the subnet that the cluster runs in. | Size `subnet_cidr` generously before the first apply. |
| `pods_cidr` / `services_cidr` | The secondary range names are fixed (`<prefix>-pods`, `<prefix>-services`), so a CIDR change plans an in-place update of the subnet's `secondary_ip_range`[^subnet-secondary], not a cluster replacement. The cluster's range-name arguments are `ForceNew`[^gke-range-names], but they do not change. | Google states the Services range "cannot be changed once the cluster is created"[^gke-alias-ips]. Do not expect an edit to either input to resize a range the cluster is using. To add Pod capacity, Google documents adding Pod ranges (discontiguous multi-Pod CIDR), which this module does not manage. | Size both ranges for the cluster's lifetime before the first apply. |
| `gcp_region` as the subnet's `region` | `google_compute_subnetwork.region` is `ForceNew`[^subnet-region] | Terraform plans to replace the subnet. `gcp_region` also sets the region of the cluster, Cloud SQL, Memorystore, router and NAT, so a region change affects most of the deployment (see the other `gcp_region` rows). | Treat the region as fixed for the life of the deployment. |
| `psa_prefix_length` (Private Services Access range) | `google_compute_global_address.prefix_length` is `ForceNew`[^psa-prefix] | Terraform plans to replace the allocated range that Cloud SQL and Memorystore use. Replacing it does not move existing instances to the new range. | Pick a prefix length with room for both Cloud SQL and Memorystore before the first apply. Google documents how to change an allocated range for an existing connection[^cloudsql-psa]; follow that procedure instead of editing this input. |
| `gcp_region` as the Cloud SQL `region` | `google_sql_database_instance.region` is `ForceNew`[^sql-region]; Google states the location "can't be changed after the instance is created"[^cloudsql-region] | Terraform plans to replace the instance. With `postgres_deletion_protection = true` (the default), the apply fails instead. | Use a cross-region replica or export and import to move the data. |
| Cloud SQL CMEK (`create_postgres_kms_key` / `existing_postgres_kms_key_id`) | `encryption_key_name` is `ForceNew` and `Optional`/`Computed`[^sql-cmek] | Adding a key, or switching to a different key, plans replacement of the instance (blocked by `postgres_deletion_protection` by default). Removing the key from the configuration does not decrypt the instance, because the argument is computed. Turning off `create_postgres_kms_key` also removes the module-created key from the configuration, so Terraform rejects the plan because of `prevent_destroy`. | Decide CMEK before the first apply. |
| `redis_tier` | `google_redis_instance.tier` is `ForceNew`[^redis-tier] | Terraform plans to replace the instance. Queued jobs in the old instance are lost. `redis_persistence_enabled` does not help: Google states RDB snapshots "are not available for manual restores"[^redis-rdb]. | Drain the queue before the change, or move data with Memorystore export and import. |
| `gcp_region` as the Memorystore `region` | `google_redis_instance.region` is `ForceNew`[^redis-region] | Terraform plans to replace the instance, with the same data loss as `redis_tier`. | Drain the queue first. |
| Hardcoded `connect_mode = "PRIVATE_SERVICE_ACCESS"` | `google_redis_instance.connect_mode` is `ForceNew`[^redis-connect-mode] | Not reachable today, because the module does not expose this value. | None. |
| `redis_transit_encryption_enabled` | `google_redis_instance.transit_encryption_mode` is `ForceNew`[^redis-transit] | Terraform plans to replace the instance, with the same data loss as `redis_tier`. | Decide in-transit TLS before the first apply. |
| Memorystore CMEK (`create_redis_kms_key` / `existing_redis_kms_key_id`) | `google_redis_instance.customer_managed_key` is `ForceNew`[^redis-cmek] | Adding, changing, or removing the key plans replacement of the instance, with the same data loss as `redis_tier`. Turning off `create_redis_kms_key` also removes the module-created key from the configuration, so Terraform rejects the plan because of `prevent_destroy`. | Decide CMEK before the first apply. |
| `gcs_location` | `google_storage_bucket.location` is `ForceNew`[^gcs-location] | Terraform plans to replace the binary-data bucket and its access-log bucket. Objects are not copied. With `gcs_force_destroy = false` (the default), deleting a non-empty bucket fails. | Pick the location before the first apply. Copy objects to a new bucket yourself if you must move. |
| `n8n_encryption_key` (or the module-generated key when it is `null`) | n8n encrypts stored credentials with this key | The key changes if you set a different `n8n_encryption_key`, or if `random_id.n8n_encryption_key` is replaced or removed from state. Recreating the core Secret alone does not change the key; the module writes the same value back. After a key change, n8n cannot decrypt stored credentials. | Back up the key before every upgrade (step 1 of [`docs/upgrading-n8n.md`](./upgrading-n8n.md)). To recover credentials encrypted under an old key, see [Restored/cloned database encryption-key continuity](./customer-managed-infrastructure.md#restoredcloned-database-encryption-key-continuity). |

## Changes that update in place, with caveats

| Module input | Provider behavior | What happens on an existing deployment | Guidance |
| --- | --- | --- | --- |
| `gke_node_type`, `gke_node_disk_size_gb`, `gke_node_disk_type` | A change to `node_config.machine_type`, `disk_size_gb`, or `disk_type` is sent as a node pool update, not a replacement[^gke-nodepool-update]. | GKE recreates the nodes with the node pool's upgrade strategy. Google states this "can cause disruption to your running workloads" and does not respect maintenance policies[^gke-machine-attrs]. An open provider issue reports one case where the apply succeeded but the node pool kept its old machine type[^gke-machine-type-issue]. | Apply during a maintenance window. Afterwards, check the node pool with `gcloud container node-pools describe` and confirm that `terraform plan` shows no changes. |
| `redis_auth_enabled` | `google_redis_instance.auth_enabled` is not `ForceNew`; the provider sends it as an update[^redis-auth] | AUTH is turned on or off in place. The module also creates or removes the Redis AUTH Secret and changes the Redis settings it passes to n8n and KEDA, so n8n pods restart. Until they do, connections that use the old setting can fail. | Apply during a quiet period and check that workers pick up queued jobs afterwards. |
| `postgres_edition` | The provider patches `edition` together with `tier` in its own update call[^sql-edition] | Google supports moving in place to Enterprise Plus and switching back to Enterprise[^cloudsql-editions]. The instance restarts. | Set `postgres_machine_type` to a tier that is valid for the new edition in the same apply. Enterprise Plus does not support shared-core tiers such as the default `db-g1-small`. |
| `postgres_ssl_mode` | `ip_configuration.ssl_mode` is not `ForceNew`[^sql-ssl-mode]; the provider sends it as an instance settings update | Google applies an SSL mode change only to new connections; open unencrypted connections stay open until they close or the instance restarts[^cloudsql-ssl-mode]. With `ENCRYPTED_ONLY`, n8n pods that still connect in plaintext are refused. | Turn on `db_postgresdb_ssl_enabled` in one apply and `ENCRYPTED_ONLY` in a second; see [PostgreSQL TLS](./postgresql-tls.md#turning-on-encrypted_only-for-a-running-deployment). |
| Cloud SQL `private_network` (always `local.effective_network_id`) | `private_network` is updated in place; only removing it forces replacement[^sql-private-network]. The module always sets it, so removal cannot happen through the module. | Cloud SQL itself can move to a different VPC in place, and Google documents this procedure[^cloudsql-psa]. In this module, though, the same network inputs also set the GKE cluster's network and the Memorystore `authorized_network`, so changing them plans replacement of those resources too. Changing `create_network` also removes or adds the module's own VPC, subnet, router and NAT. | Treat a network change as a planned migration of the whole deployment, not a Cloud SQL setting. |
| GCS CMEK (`create_gcs_kms_key` / `existing_gcs_kms_key_id`) | The bucket's `encryption` block is updated in place[^gcs-encryption] | The new default key applies to objects written after the change. Existing objects stay encrypted with the old key. Turning off `create_gcs_kms_key` also removes the module-created key from the configuration, so Terraform rejects the plan because of `prevent_destroy`. | Keep the old key and its key versions enabled, and keep the bucket's access to them, while old objects still use it. |
| `n8n_fqdn` | `google_dns_record_set.n8n` uses `for_each` keyed by hostname | When the module manages Cloud DNS, Terraform creates a record for the new hostname and deletes the old one. The record TTL is fixed at 300 seconds. With `tls_mode = "google_managed"`, the module updates its single `ManagedCertificate`, and Google deletes and recreates the certificate behind it[^gke-managed-cert]. HTTPS can fail for every hostname on that certificate until the new one is active. | Plan a maintenance window. To keep the old hostname working, add it to `n8n_additional_domains`. |
