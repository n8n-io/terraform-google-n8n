## Context

See `proposal.md` for scope and `parity-matrix.md` for the source-backed disposition of every AWS 0.5.0 changelog item. This design targets the Google baseline at HEAD and chart `1.10.1` moving to `1.11.0`, not AWS resource names or AWS's chart-1.11.0 assumptions (KEDA `listName`, chart-managed `/mcp/` Ingress rule) that do not reach this module.

Two items from `parity-matrix.md` are deliberately out of this change by explicit user decision: `n8n_worker_pools`/`n8n_worker_extra_env` (deferred until the upstream chart ships a numbered release carrying the feature) and the CI `TF_VERSION`/`TFLINT_VERSION` currency bump (tracked as a separate version-currency decision, not a parity one, per `AGENTS.md`'s documented rationale for pinning the CI floor to 1.9.x).

Terraform 1.9.8 is the CI floor and must stay provable at that version throughout this change, since the Kubernetes provider bump and validation changes below are exactly the kind of expression that behaves differently on newer CLIs (see `AGENTS.md`, "CI pins Terraform 1.9.x").

## Goals and non-goals

- Bump the Kubernetes and `time` provider floors and the default n8n chart version, verified with a real in-place upgrade the same way AWS verified its own bump, not just a passing plan.
- Close the four real validation/coverage gaps this round's research found (DNS/name label hygiene, self-signed cert CN length, checkov's opt-in-resource blind spot, unpinned exporter image), each because it is independently a bug, not because AWS also fixed it.
- Add the docs/tooling AWS added (`versioning.md`, drift/coverage/diff scripts, Istio doc, markdownlint CI) adapted to Google's actual pin set, script conventions (plain bash under `tests/scripts/`, no Taskfile), and example set.
- Bring every example that lets the module own Cloud SQL/GCS to the same documentation and passthrough completeness `examples/small` should already have.
- Do not build `n8n_worker_pools`, bump the RDS-analog PostgreSQL major, install metrics-server, or invent a Cloud SQL final-snapshot/automated-backup-deletion control Google has no equivalent for.
- No live apply is required for implementation acceptance except the one documented in-place-upgrade verification for the breaking provider bump, which is the same bar AWS held itself to. Everything else is plan-time/render-time proof.

## Decisions

### 1. Version and chart bumps, verified by a real upgrade

Bump `versions.tf`'s `kubernetes` constraint from `~> 2.0` to `~> 3.0` and `time` from `~> 0.12` to `~> 0.14`. Apply the same `kubernetes` bump to `modules/controllers/versions.tf`, `modules/controllers/examples/direct-use/versions.tf`/`providers.tf`, and every `examples/*/providers.tf`. No `.terraform.lock.hcl` is committed anywhere in this repo, so there is nothing to regenerate. Do not rename any of the 8+ unversioned `kubernetes_namespace`/`kubernetes_secret` resources (`n8n.tf`, `keda.tf`, `examples/cloudflare/dns.tf`) to their `_v1` twins: the provider has no `moved` support across that rename (same open upstream issue AWS cited), so renaming would force every existing deployment to destroy and recreate its namespace. Accept the cosmetic "Deprecated Resource" warning as AWS did.

Add a Compatibility subsection to `README.md` (today it has only "Stability & versioning", no provider-floor listing) carrying the Kubernetes-provider-3.0 upgrade note, including AWS's caveat that a root module declaring its own `kubernetes ~> 2.0` constraint must widen it first or `init` cannot satisfy both, and linking `docs/versioning.md`. Link `docs/versioning.md` from `docs/upgrading-n8n.md`'s opening paragraph as well.

Bump the default `n8n_chart_version` from `1.10.1` to `1.11.0`. Re-run `tests/scripts/check-n8n-chart.sh` against it and confirm no rendering regression; document in the changelog, mirroring AWS's own note, that chart 1.11.0's two behavior changes (KEDA `listName` default, chart-managed `/mcp/` Ingress rule) are already inert here because this module sets `redis.worker`'s `listName` itself and manages its own Ingress `/mcp` route rather than the chart's.

Verify the provider bump live, the same way AWS did: apply `examples/small` on the current pins, then `terraform init -upgrade` and `terraform plan` on the new pins, and confirm the diff is limited to the expected in-place `helm_release.n8n` version bump with no unexpected action on any `kubernetes_namespace`/`kubernetes_secret`/`kubernetes_ingress_v1`/`kubernetes_horizontal_pod_autoscaler_v2`/`kubernetes_storage_class_v1` resource. Record the actual plan output in the verification report; do not claim this was checked without running it.

### 2. Validate the actual DNS-1123/x509 rules, not just total length

`n8n_fqdn` (`variables.tf:61-64`), `n8n_additional_domains` (`variables_gcp.tf:863-890`), and `n8n_image_pull_secrets` (`variables.tf:340-358`) each anchor only the outermost string today: none bounds an individual dot-separated label to 63 characters, and the middle character classes admit empty labels (`a..b`) and labels starting/ending with a hyphen anywhere but the very first character of the whole string. Add a per-label check to each: split on `.`, and for every element assert `1 <= length <= 63` and `can(regex("^[a-zA-Z0-9]([a-zA-Z0-9-]*[a-zA-Z0-9])?$", label))` (Kubernetes/DNS-1123 label shape). Keep every existing whole-string check (total length, malformed-shape regex, wildcard rejection, duplicate rejection, canonical-hostname repetition, the 100-domain `ManagedCertificate` cap) unchanged; this is additive tightening, not a replacement.

Add a `precondition` on `tls_self_signed_cert.self_signed` (`dns.tf:65-77`) rejecting `var.n8n_fqdn` over 64 characters when `tls_mode = "self_signed"`: RFC 5280 caps a certificate Common Name at 64 octets, tighter than the 253-octet whole-name limit, and today an over-length hostname fails deep inside the `tls` provider mid-apply rather than at plan. The `google_managed`/`custom`/`secret` paths keep only the existing 253-character rule, since they are SAN-bearing, not CN-bearing, matching AWS's own split between its ACM CN precondition and its broader SAN validation. No example-level CN validation is needed (unlike AWS's `cloudflare`/`godaddy`): the Google `cloudflare` example's `cert-manager` `Certificate` sets only `dnsNames`, no `commonName` (`examples/cloudflare/dns.tf:85`), and `godaddy` uses a Google-managed SAN certificate. No Google example declares `n8n_image_pull_secrets`, so that fix is root-only too.

### 3. Close the checkov opt-in-resource blind spot and pin the exporter image

`redis_exporter_enabled` defaults `false`, so every resource gated by it in `observability.tf` (`count = var.redis_exporter_enabled ? 1 : 0`) plans at count 0 by default; checkov answers every check on a count-0 resource `UNKNOWN` and silently drops it from the report, so the exporter's `CKV_K8S_*` checks have never actually run against a real resource. Add a second checkov invocation, local (`tests/scripts/check-checkov.sh`, mirroring AWS) and CI, against a fixture that sets `redis_exporter_enabled = true` (a new `tests/checkov/opt-in.tfvars`), and fail the job if that pass does not reach `kubernetes_deployment_v1.redis_exporter`. Inventory whatever that pass surfaces rather than pre-assuming AWS's list. One finding is already known and deliberate: `CKV_K8S_11` (no CPU limit) matches the trade already reasoned in the resource comment (`observability.tf:164-166`); annotate it with a narrowly scoped, explained `checkov:skip` for that one check only, as `AGENTS.md` permits for a genuine documented exception. Add `terraform test` assertions pinning the exporter's security context (non-root, read-only root filesystem, dropped capabilities), memory limit, image digest, and probes, the same fields checkov itself cannot independently verify from a Terraform plan. Record the corrected diagnosis in `AGENTS.md`'s "Static analysis" section, as AWS did, so a future count-gated resource gets an opt-in fixture entry.

Pin `redis_exporter_image`'s default (`variables_gcp.tf:605`, currently `oliver006/redis_exporter:v1.90.0`, tag only) by digest as well as tag. Resolve the actual multi-arch manifest digest for that exact tag at implementation time (`docker manifest inspect` or an equivalent registry query); do not copy AWS's digest string without independently verifying it resolves to the same tag, since a wrong digest silently breaks every enabled deployment's next apply.

### 4. Add the docs/tooling AWS added, adapted to what actually exists here

Add `docs/versioning.md` inventorying every pin this module makes: the 8 providers in `versions.tf` (`google`, `google-beta`, `kubernetes`, `helm`, `kubectl`, `tls`, `random`, `time`), `n8n_chart_version`, `keda_chart_version`, `postgres_version`, `kubernetes_version` (GKE), and the CI toolchain (`TF_VERSION`, `TFLINT_VERSION`, the checkov action ref, `TERRAFORM_DOCS_VERSION`). Classify each into the same three bump tiers AWS used (patch-safe, minor-required, verification-required) and link it from `AGENTS.md`, the new `README.md` Compatibility subsection, and `docs/upgrading-n8n.md`. Where the three new scripts below share a "read a variable's default out of `variables.tf`" helper, put it once in `tests/scripts/lib/tf-defaults.sh` as AWS did, not three copies.

Add `tests/scripts/check-version-drift.sh` reporting, never auto-bumping, every pin reachable from a public API: Terraform providers via the registry API, the CI toolchain, the two Helm charts this module installs (n8n, KEDA) via their chart repositories, and `kubernetes_version` against GKE's own release-channel/version API (not EKS's; GKE's supported-version surface differs and has no `endoflife.date`-style table AWS used). Wire a weekly GitHub Actions workflow that runs it and files/updates a single tracking issue, mirroring AWS's job shape.

Add `docs/helm-chart-coverage.md` (the pinned chart's `values.yaml` keys and what each maps to, or an explicit "not surfaced" note) and `tests/scripts/check-helm-chart-coverage.sh`, which fails when the doc's declared chart version disagrees with `n8n_chart_version`'s default or the pinned chart's `values.yaml` gained a top-level key the doc never mentions. Add `tests/scripts/chart-values-diff.sh` (a `helm show values` diff between the pinned version and a candidate, argument-driven) and document invoking it directly by path; do not add a Taskfile or a `task` target, since neither exists anywhere in this repository and introducing one for a single script would be a new tooling dependency, not currency.

Add `docs/istio-ingress.md` covering this module's `create_ingress = false` contract expressed as `Gateway`/`VirtualService` instead of `kubernetes_ingress_v1`, reusing `examples/split-ingress`'s existing route-prefix rules (no main-service catch-all on the public route; route families ordered before any internal catch-all) and its "200 with an HTML body" webhook-misroute trap. Purely additive: no new example, no CI matrix entry, no new module input or output.

Add a `markdownlint` CI job linting `README.md`, `AGENTS.md`, and `docs/*.md` (no `CONTRIBUTING.md` exists in this repo to include), wrapping the generated `terraform-docs` block in `<!-- markdownlint-disable -->`/`<!-- markdownlint-restore -->` the same way AWS does, to suppress false positives from generated placeholder tokens and bare URLs without hand-editing generated content.

### 5. Bring every Cloud-SQL/GCS-owning example to documentation and passthrough completeness

Add a "Production considerations" README section, matching `examples/small`'s eventual shape, to every example that lets the module create Cloud SQL and/or GCS: `small`, `medium`, `large`, `cloudflare`, `godaddy`, `split-ingress`, `customer-managed-redis`, `customer-managed-cluster`, `customer-managed-gcs`. Name `postgres_deletion_protection`, `postgres_backup_retained_backups`, `postgres_transaction_log_retention_days`, and `gcs_force_destroy` as the caller-facing knobs; `customer-managed-gcs` gets only the Cloud SQL rows since its own bucket is caller-supplied. `customer-managed-everything` gets no such section, since it owns neither layer.

Add `postgres_backup_retained_backups`/`postgres_transaction_log_retention_days` as nullable passthrough variables (defaulting to the module's own default, i.e. `null`) to every example above that does not already have them; `postgres_deletion_protection`/`gcs_force_destroy` are already wired everywhere and need no change. Each example's `tests/defaults.tftest.hcl` gets an assertion at default and with an explicit non-null value. Each "Production considerations" section links `docs/destroy-cleanup.md`'s existing "Deletion protection" and CMEK-key sections rather than duplicating the retained-data-under-a-destroyed-key warning into nine READMEs. No input-echo outputs (`postgres_deletion_protection`, `gcs_force_destroy`, etc.) are added: nothing in this repo consumes them, and the existing `checks.tf` ignored-input warnings (`:95`, `:201`) already cover the misconfiguration AWS's new `check` guards.

`n8n_additional_domains` is passed through by no Google example today, so AWS's "explain why `cloudflare`/`godaddy` omit it" fix has no meaning here until the examples that can take it have it. Add it as a passthrough (default `[]`) to `small`, `medium`, `large`, `customer-managed-cluster`, `customer-managed-redis`, `customer-managed-gcs`, and `customer-managed-everything` (`split-ingress` composes its own host set and is excluded, matching AWS). Then document, in `examples/cloudflare/README.md` and `examples/godaddy/README.md`, why neither passes it through: each issues its own single-hostname certificate/DNS record (Cloudflare via `cert-manager` `dnsNames = [var.n8n_fqdn]`, GoDaddy via a single A-record) and the module cannot add Subject Alternative Names to a certificate it did not itself issue.

Add `scripts/check-example-parity.sh`, diffing every `examples/*/variables.tf` variable-name set against `examples/small`'s and failing on any name present on only one side that is not in that example's own allowlist (DNS-provider credentials, `customer_managed_*` stand-ins, `split-ingress`'s own routing inputs, `large`'s BYO-certificate inputs), and, as AWS's does, failing when an example still lets the module create Cloud SQL or GCS but its README has no "Production considerations" section. Wire it as a local-only check for now (`AGENTS.md`'s local development loop), matching AWS's own "not yet in CI" caveat for the same script; add it to CI in a follow-up once it has run clean against the current tree.

### 6. Keep the contributor surface in step

Every new script is added to `AGENTS.md`'s local development loop and to `tests/scripts/README.md`; the checkov opt-in blind spot and its fixture requirement go into `AGENTS.md`'s "Static analysis" section. `CHANGELOG.md`'s `[Unreleased]` gains a **BREAKING** entry for the Kubernetes provider bump (with the same "what moves on apply" framing AWS used), plus entries for the `time`/chart bumps, the tightened validations (framed as "always rejected downstream, now rejected at plan"), the exporter digest pin, and each new doc/script. `README.md`'s generated reference block is refreshed with `terraform-docs` after every variable change (CI-gated).

## Risks and mitigations

- The Kubernetes provider 3.0 bump is breaking for any caller pinned to `~> 2.0`. Document the same upgrade note AWS did (pin `~> 2.0` explicitly to defer, or read the note before upgrading) and prove the in-place upgrade path with a real apply before merging.
- A wrong `redis_exporter_image` digest silently breaks every deployment with `redis_exporter_enabled = true` on its next apply. Verify the digest against the live registry manifest, not by copying AWS's string.
- Tightening `n8n_fqdn`/`n8n_additional_domains`/`n8n_image_pull_secrets` validation can reject a previously-accepted (but always-broken-downstream) value on an existing caller's next plan. This is intentional: document it as a breaking validation change in the changelog, matching AWS's own framing ("always going to be rejected by Kubernetes, now fails at plan instead of apply").
- The version-drift and chart-values-diff scripts depend on external registry/API availability; they must fail loudly and never silently no-op when a lookup fails, and must never auto-write a version bump.
- Checkov's second opt-in pass adds CI time and a second fixture to keep in sync with the module's actual count-gated resources. Document that any future count-gated resource needs an entry in the opt-in fixture, the same way `AGENTS.md`'s "Static analysis" section already documents the original blind spot for `redis_exporter`.

## Migration plan

1. Publish a compatibility note for this release: the Kubernetes/`time` provider bumps, the `n8n_chart_version` default bump, and the newly-rejected DNS/pull-secret/image-tag shapes. No automatic state migration is promised, consistent with this module's pre-release stability contract.
2. Before applying, back up Terraform state. Run `terraform init -upgrade` and read the plan; expect only the documented in-place `helm_release.n8n` updates and cosmetic Kubernetes-resource deprecation warnings.
3. If `terraform plan` newly rejects an existing `n8n_fqdn`, `n8n_additional_domains` entry, or `n8n_image_pull_secrets` entry, correct the value; downstream (GKE Ingress/ManagedCertificate/Kubernetes Secret) was always going to reject it too.
4. Enabling `redis_exporter_enabled = true` on an existing deployment rolls the exporter pod once to pick up the pinned digest; no other pod is affected.
5. Rollback: pin `kubernetes = "~> 2.0"` and `n8n_chart_version` back to the prior default; no resource address changed in this round, so a plain revert of the module source pin is sufficient.
