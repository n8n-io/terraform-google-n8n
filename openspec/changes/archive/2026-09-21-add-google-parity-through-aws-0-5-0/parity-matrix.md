# AWS through 0.5.0 applicability review

## Baselines and evidence

- AWS tag: [`0.5.0`](https://github.com/n8n-io/terraform-aws-n8n/releases/tag/0.5.0), [`CHANGELOG.md`](https://github.com/n8n-io/terraform-aws-n8n/blob/0.5.0/CHANGELOG.md).
- Google baseline: this repository at HEAD (`128e5ad`, merge of the completed `add-google-parity-through-aws-0-4-0` change plus follow-on fixes through 2026-09-21).
- Review scope is only the 0.4.0 to 0.5.0 diff. Anything already dispositioned in the archived `add-google-parity-through-aws-0-4-0/parity-matrix.md` is not re-reviewed here.
- Google-side evidence gathered by direct read/grep of this repository at HEAD: `versions.tf`, `variables.tf`, `variables_gcp.tf`, `locals.tf`, `n8n.tf`, `cloudsql.tf`, `gcs.tf`, `observability.tf`, `dns.tf`, `modules/controllers/*`, every `examples/*`, `docs/*`, `tests/scripts/*`, `.github/workflows/terraform-tests.yml`.

`Port` means missing cloud-independent behavior. `Adapt` means the goal applies but Google requires a different contract. `Existing` means retain and regression-test, not reimplement. `Exclude` means no change in this plan; a rationale follows.

## Fixes and security

| AWS item | Decision | Google evidence and planned action |
| --- | --- | --- |
| `n8n_image_pull_secrets` per-label 63-char bound | Port | Real gap confirmed: Google's validation (`variables.tf:340-358`) checks a DNS-1123-subdomain-shaped regex plus a 253-char *total* length and dedupe, but never bounds an individual dot-separated label to 63 characters, and the regex's `[a-z0-9.-]*` middle class admits empty inner labels (`a..b`). Add the same per-label bound AWS added. |
| `n8n_fqdn`/`n8n_additional_domains` DNS label hygiene | Port | Real gap confirmed: `n8n_fqdn` (`variables.tf:61-64`) and `n8n_additional_domains` (`variables_gcp.tf:863-890`) both anchor only the outermost string; neither bounds a label to 63 characters nor rejects an empty label, or a label starting/ending with a hyphen, anywhere but the very first character of the whole string. Tighten both to the actual rule the downstream consumers enforce: GKE `ManagedCertificate`/Ingress `host` and n8n's own `N8N_HOST`/`WEBHOOK_URL` handling. |
| Certificate common-name length precondition | Adapt | AWS's ACM 64-octet CN bound has a direct Google analog: `tls_self_signed_cert.self_signed` (`dns.tf:65-77`) sets `subject.common_name = var.n8n_fqdn` (`dns.tf:70`) with no length guard, so an over-64-character `n8n_fqdn` on `tls_mode = self_signed` fails deep in the `tls` provider instead of at plan. Add a `validation`/`precondition` bounding `n8n_fqdn` to 64 characters specifically on that path (the SAN-bearing `google_managed`/`custom` paths keep the 253-character rule only, matching AWS's own split between its ACM CN precondition and its broader SAN validation). |
| checkov never scans the opt-in `redis_exporter` Deployment | Port | Real gap confirmed: `redis_exporter_enabled` defaults `false` and every count-gated resource in `observability.tf` (`count = var.redis_exporter_enabled ? 1 : 0`, `observability.tf:16-17,229-230`) plans at 0 by default with no `checkov:skip` comments, so checkov answers every check `UNKNOWN` and drops it silently, identical to the AWS root cause (#120's corrected diagnosis, not a resource-type registration gap). Add a second checkov pass in CI and locally against an opt-in-enabled fixture (`redis_exporter_enabled = true` plus whatever else is currently count-gated), fail the job if that pass does not reach the exporter resource, and add `terraform test` assertions pinning its security context, capabilities, memory limit, digest pin, and probes. |
| `redis_exporter_image` digest pin | Port | Real gap confirmed: Google's default is `oliver006/redis_exporter:v1.90.0` (`variables_gcp.tf:605`), tag only, no digest, the exact same tag AWS pinned by digest in 0.5.0. Add the matching `@sha256:...` multi-arch-index digest (verify the digest against the actual published manifest at implementation time; do not copy AWS's digest string without independent verification, since a Google-side `docker manifest inspect`/registry lookup is required to confirm it resolves to the same tag). |
| Missing "Production considerations" sections | Port | Real gap confirmed: none of Google's 10 example READMEs has such a section (closest analogues are `examples/large`'s "Things to watch..." and `examples/cloudflare`'s "Notes"). Add the section to every example that lets the module own Cloud SQL and/or GCS (all except `customer-managed-everything`), naming `postgres_deletion_protection`, `postgres_backup_retained_backups`, `postgres_transaction_log_retention_days`, and `gcs_force_destroy` as the caller-facing knobs, mirroring `examples/small`'s eventual table. |
| Backup-tuning passthrough gap in examples | Port | Real gap confirmed: `postgres_deletion_protection` and `gcs_force_destroy` are already declared and passed through in every example (e.g. `examples/small/variables.tf:71-81`, `main.tf:30-31`), but `postgres_backup_retained_backups`/`postgres_transaction_log_retention_days` are module-only, passed through nowhere. Add both as nullable passthrough variables to every example that owns Cloud SQL, mirroring AWS's #134/#136 fix and its own `check-example-parity`-style rationale. |
| `db_delete_automated_backups` / final-snapshot controls | Exclude | No Google equivalent exists or is being invented: Cloud SQL has no exportable "final snapshot on delete" concept comparable to RDS's, and deleting a Cloud SQL instance's automated backups is not independently controllable the way AWS's flag is. Repo-wide grep for `final_snapshot`/`snapshot_identifier` returns zero matches on both sides for the same reason. Document the boundary in `docs/destroy-cleanup.md`, matching the 0.4.0 matrix's own precedent for excluding an AWS-only lifecycle knob (`apply_immediately`) rather than inventing a Google analog that doesn't exist. |
| `scripts/check-example-parity.sh` | Port | Absent (`scripts/` contains only `preflight.sh`). Add the same variable-name-diff checker against `examples/small`'s `variables.tf`, adapted to Google's 10 examples and their own per-example allowlist reasons (DNS-provider credentials, `customer_managed_*` stand-ins, `split-ingress`'s own routing inputs, `large`'s BYO-certificate inputs). Include AWS's second check: fail when an example still lets the module create Cloud SQL or GCS but its README has no "Production considerations" section. Wire it as a local-only check first, matching AWS's own "not yet in CI" caveat. |
| `cloudflare`/`godaddy` silently omit `n8n_additional_domains` | Adapt | AWS's fix presumes `small`/`medium`/`customer-managed-*` already pass `n8n_additional_domains` through and only the two DNS-variant examples omit it. Google's situation is worse: **no** example passes it through (grep across `examples/*/variables.tf` matches nothing; module-level only at `variables_gcp.tf:863`), so a "why cloudflare/godaddy omit it" note would be meaningless on its own. First add the passthrough to every example that can take it (`small`, `medium`, `large`, `customer-managed-cluster`, `customer-managed-redis`, `customer-managed-gcs`, `customer-managed-everything`; `split-ingress` composes its own hosts), then add AWS's explanation to `cloudflare`/`godaddy`: each issues its own single-hostname certificate/DNS record (Cloudflare `cert-manager` with `dnsNames = [var.n8n_fqdn]`, `examples/cloudflare/dns.tf:85`; GoDaddy a single A-record, `examples/godaddy/dns.tf:8-13`) and the module cannot add SANs to a certificate it did not issue. |
| `db_backup_retention_period` `nullable = false` fix | Exclude | Different design already, no bug: Google's `postgres_backup_retained_backups` (`variables_gcp.tf:188-197`) is deliberately nullable with `default = null` meaning "leave Cloud SQL's own default retention," not AWS's always-numeric input with an accidentally-`nullable = true` default. No caller-visible bug exists to fix. |
| `helm_release.n8n` top-level `replicaCount` set explicitly | Existing | Already done: `n8n.tf:258` sets `replicaCount = local.n8n_effective_main_replica_count` unconditionally, alongside `multiMain.replicas` (`n8n.tf:253`), as part of the 0.4.0 topology work. No action. |
| `smoke-test.sh` multi-main misdetection | Existing, no bug | Google's detection (`tests/scripts/smoke-test.sh:1359-1394`) classifies topology directly from `kubectl get deployment n8n-main -o jsonpath='{.spec.replicas}'` and `.spec.strategy.type`, not from probing the chart's `configMapKeyRef`-only env var's static `.value` field the way AWS's script did. The separate `N8N_MULTI_MAIN_SETUP_ENABLED` checks (`:495-503`, `:1384-1392`) use `kubectl exec ... printenv`, which reads the resolved runtime value, not the manifest field, so they are not exposed to the same bug. No action. |
| `cloudflare`/`godaddy` example-level 64-character `n8n_domain` validation | Exclude | AWS needed it because those examples issue an ACM certificate whose Common Name is the hostname. Google's `cloudflare` example's `cert-manager` `Certificate` sets only `dnsNames` (`examples/cloudflare/dns.tf:85`), no `commonName`, so the hostname is a SAN and the RFC 5280 64-octet CN cap does not apply; `godaddy` uses a Google-managed certificate, also SAN-based. The only CN-bearing path in this repo is the root module's `tls_self_signed_cert` (covered by the "Certificate common-name length precondition" row). No example-level validation is warranted. |
| `n8n_image_pull_secrets` fix "in root and all 10 examples" | Existing, root-only | AWS's examples each pass `n8n_image_pull_secrets` through with their own copy of the validation, so its fix touched 11 files. No Google example declares `n8n_image_pull_secrets` (grep across `examples/*/variables.tf` matches nothing), so the per-label fix is root-only (`variables.tf:340-358`). Not adding the passthrough: it is not a 0.5.0 item, and `check-example-parity.sh` compares examples against `examples/small`, not against the root. |
| `s3_force_destroy_requires_module_managed_bucket` check and the RDS clause in `rds_tuning_requires_module_managed_database` | Existing | Google already warns on both: `checks.tf:95` covers `postgres_deletion_protection` (plus backup retention, transaction-log retention, query logging) when `create_postgres_instance = false`, and `checks.tf:201` covers `gcs_force_destroy` when `create_gcs_bucket = false`. No action. |
| `rds_*` / `s3_force_destroy` outputs echoing the deletion controls in effect | Exclude | Pure echoes of inputs the caller already set; nothing in this repo consumes them (`outputs.tf` has no such outputs today and `tests/scripts/smoke-test.sh` reads none). The 0.4.0 round added outputs only where the smoke test or a caller-owned ingress needed them. Adding four input-mirror outputs is surface area without a consumer; skip unless a consumer appears. |
| README "Deletion protection and teardown" section, including retained-data-under-a-destroyed-CMEK-key warning | Existing, link it | `docs/destroy-cleanup.md` already has a "Deletion protection" section (`:32`) and the CMEK `prevent_destroy`/scheduled-destruction discussion (`:63-71`, "once nothing encrypted with it must remain readable"). Rather than duplicating it into `README.md`, link it from every new example "Production considerations" section and from `README.md`'s Stability & versioning area. |
| `docs/versioning.md` linked from `README.md` Compatibility and `docs/upgrading-n8n.md` | Port | `README.md` has a "Stability & versioning" section (`:285`) but no "Compatibility" section listing provider floors; `docs/upgrading-n8n.md` exists (`docs/`). Add a Compatibility subsection to `README.md` carrying the Kubernetes-provider-3.0 upgrade note (including AWS's "widen your own `~> 2.0` constraint first" caveat) and the `versioning.md` link, and add the link to `docs/upgrading-n8n.md`'s opening paragraph. |

## Explicit limitations retained

No worker pools (deliberately omitted this round pending a numbered upstream chart release), no automatic RDS-major-style PostgreSQL bump, no metrics-server install, no Cloud-SQL final-snapshot/automated-backup-deletion control, and no `task`/Taskfile dependency are introduced.
